# 应用安全现状（静态代码复核）

> 日期：2026-10-10。基于当前代码和 Vercel 环境变量名称的只读检查；不是渗透测试或完整线上验收。未读取密钥值、未提交认证表单、未创建测试账号。

## 已看到的保护

- **密码与登录：** 网页把邮箱和密码交给 Neon Auth SDK；应用数据库不保存密码。后端用 JWKS 验证 bearer JWT 的签名、issuer、subject 和有效期，再以 `sub` 作为账号 ID。
- **记录权限：** 发布、查看个人记录、关闭和删除都要求有效登录；个人记录查询及修改/删除语句都按 `owner_id` 限定。
- **SQL 注入：** 当前业务查询使用固定 SQL 和参数绑定；静态检查未发现把用户输入拼接进 SQL 的路径。表结构迁移也是固定语句。
- **重复账号：** 账号由 Neon Auth 管理，应用没有自建用户表或注册接口。显示名称不是唯一标识，同名账号可以存在；邮箱重复注册交给 Neon Auth 判定。尚未独立核实其大小写规范化和生产端重复注册行为，因此不能承诺同一人只能有一个账号。
- **图片上传：** 限定 JPEG/PNG/WebP，限制字节数和宽高，重新编码并移除 EXIF；生产图片走 Blob。
- **秘密值：** API key、数据库和 Blob 凭证只从服务端环境变量读取，不由公开配置接口返回。最近只核对了环境变量名称，未读取值。
- **清理接口：** 过期清理要求 `CRON_SECRET` bearer 值，并用常数时间比较；线上无密钥请求曾返回 401。

## 限制和未核实项

- 用户决定暂不加应用自定义登录频率限制；Neon Auth 自身的防滥用策略未核实。
- 未逐项验证邮箱大小写变体、重复注册、密码策略、邮件验证、账户恢复，以及退出登录后的边界行为。
- 未做端到端注册/登录、跨账号越权、上传/删除、DeepSeek 调用或过期清理演练；未做渗透测试。
- 公开记录和图片可被访客访问；没有认领验证、管理员审核或举报处理流程。公开记录不要放电话、住址、证件号码等敏感信息。
- JWT 验证代码关闭 audience 校验，因为 token 面向 Neon 服务；实际 token 和受保护请求仍应按 Neon 文档进行人工验收。

## 2026-10-10 追加线上只读检查

- `/api/health`、`/api/config`、`/api/records`、`/login`、`/my-records` 和 `/static/app.js` 均返回 HTTP 200；公开记录当前为空。
- 对 `/api/records` 发送字段完整但没有登录凭证的合成 multipart 请求，得到 HTTP 401“请先登录后再操作”；未创建记录、未上传有效照片，也未调用 DeepSeek。这证明路由可达及未登录发布受保护。
- 该请求没有验证有效登录后的发布、图片 Blob 写入、AI 调用、匹配结果或清理流程；用户先前截图中的登录后 HTTP 404 仍未定位。

## 结论

目前可确认存在基础认证、记录所有权检查、参数化 SQL、图片输入限制和服务端密钥存储，适合作为 FYP 演示原型的安全基线。不能据此称为生产级安全或安全测试已完成。账号流程和跨账号授权检查仍需用专门测试账号及非敏感数据验收。
