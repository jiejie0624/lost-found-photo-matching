# 第三章：研究方法（草稿）

> **状态：** 依据当前原型、离线评估脚本和待讨论研究方案整理。研究问题、采集方式、样本规模、同意、DeepSeek 第三方处理和统计方案均尚未得到导师/学校确认。本章不代表伦理批准；未获批准前，不招募参与者、不收集真实研究图像、不调用 API 处理研究资料。所有方括号项目需按最终审批填写；不得虚构数据、许可、日期或实验步骤。

## 3.1 研究目标与设计

本研究拟比较三种失物候选排序方法，并测量视觉 API 带来的排序变化、运行延迟、失败率和实际费用。设计为同一查询、同一候选池和同一人工配对标签上的离线配对比较。系统给出参考顺序，不判断所有权或自动确认认领。

建议的主要研究比较是完整视觉方法 C 对表单基线 A 的 Hit Rate@5 差值；照片属性方法 B 对 A、照片重排方法 C 对 B 用于描述组件增量，作为次要/探索性分析。该主次安排尚待导师确认，并须在 test 集结果可见前冻结。

本研究测量固定数据集中的检索排序表现，不等同于现实中失物找回率、系统长期运行效果或模型对物品身份的证明。若数据来自受控拍摄，论文需明确它是受控场景，不是实际失物个案。

## 3.2 研究对象与数据来源

数据拟由 `[导师/学校批准的数据来源]` 提供。一个具体物品身份作为一个 `item_group_id`；围绕该物品建立至少一条查询记录和一条候选记录，并由有依据的来源确认它们是同一件物品。相似类别、颜色或款式但非同一件物品的记录作为困难负例。标签来源、拍摄者、采集时间、地区和纳入方式均由批准后的采集记录填写。

可供导师决定的方案是：在获得批准后，由物品提供者提供普通日常物品，分别在不同角度、背景或光线下拍摄，构造失物/拾获方向的模拟记录。此方案尚未执行；样本数、物品类别、每件物品拍摄数量、拍摄条件和是否需要真实参与者均待审批确定。若改用公开数据，须逐一核对数据许可、身份标签、候选结构与 DeepSeek 处理授权；CUTE 的图数差异未解释，而且它没有失物/拾获与时空信息，不能替代主要失物配对数据。

## 3.3 系统与比较方法

系统实现以仓库版本和部署检查为准：响应式 HTML/CSS/JavaScript 网页、Python/FastAPI 后端；本地开发使用 SQLite，本地图片经处理后存于项目目录；云端使用 Neon PostgreSQL 保存记录、Vercel Blob 保存图片、Neon Auth 管理用户登录。论文只描述经代码和运行证据确认的行为，不把已部署等同完整端到端验收。

三种排序方法如下：

1. **A：表单基线。** 按当前匹配规则使用用户填写的标题、类别、颜色、地点、时间和文字说明，不使用模型输出的照片属性。
2. **B：表单加视觉属性。** 在相同表单分数上增加 DeepSeek 提取的可见类别、颜色、清楚可见的品牌和外观特征。没有获批或没有明确同意的记录不进入视觉分析。
3. **C：候选照片直接比较。** 先按 B 选出前五个候选，再在同一 API 请求中比较查询照片和候选照片。当前原型将启发式分数的 45% 与模型返回照片参考分的 55% 合并排序；照片分数为 0–100 的排序信号，不是概率、身份判定或所有权证明。只有查询与候选两方都符合获批的 AI 处理条件时才可比较。

方法 B/C 使用 DeepSeek API。当前实现配置名为 `deepseek-flash`；正式实验须记录当时官方模型版本、调用日期、提示词版本、图像预处理和失败情况。使用 API 前须取得学校对第三方处理、跨境处理与数据保存的书面指导。若未获许可，停止相关视觉方法，不以真实研究图像测试或调试。

## 3.4 标签与标注程序

配对表每一行对应一个失物查询与一个拾获候选。标签含义为：`1` = 有可靠依据确认同一件具体物品；`0` = 有可靠依据确认是不同物品；`uncertain` = 证据不足或意见不一致。`label_confidence` 记录 `high/medium/low`，理由字段只写可复核的物品证据，不记录身份信息。

每个查询必须覆盖其同一 split 候选池内全部拾获记录；未判断的配对应显式标记 `uncertain`，不能省略，也不能自动当作负例。建议至少对 `[导师批准的比例]` 配对进行双人独立标注。保留标注者原始结果，报告共同标注数、原始一致率、混淆表和 Cohen’s kappa，再按预定流程人工裁决；kappa 不作为自动认可标签的门槛。

正例应由能确认来源的人或其他批准的可追溯证据确认。同类别、同颜色、同品牌或图像模型高分本身均不足以证明同一件实物。模型输出不能用于构造 ground truth。

## 3.5 开发/测试划分与防泄漏

先确定物品身份及必要的贡献者/采集批次分组，再划分 `development` 与 `test`。同一 `item_group_id` 的全部照片、方向记录、重复记录、标注与模型分数必须留在同一个 split。若同一参与者提供多件物品，或多个物品共享明显拍摄布景，应依批准方案尽可能将其整体置于同一 split；若不可行，记录限制。

每条 lost 查询的候选池由同一 split 中的全部 found 记录构成。各方法必须使用完全相同的查询、候选与冻结标签。只允许在 development 集调整提示词、排序权重、图像预处理及候选数；test 的标签不可用于调参，最终 test 照片分数应在流程冻结后一次性生成并留档。

## 3.6 主要指标与统计分析

- **唯一建议的确认性主要指标：Hit Rate@5。** 对每条查询，检查排序前五名是否至少有一个达到预定置信度门槛的确认正例，再按查询取宏平均。主要差值为 C−A。
- **次要指标：Recall@5、MRR@5。** Recall@5 衡量确认正例中进入前五名的比例；MRR@5 依据排名最高的正例计算倒数排名，无前五名正例则为 0。
- **组件分析：** B−A、C−B 及其他 K 值作为次要/探索性结果完整报告，不因结果显著与否改变主要结论。若导师要求组件比较作确认性检验，应在 test 前确定多重比较处理。
- **不确定标签：** 低于预设置信度门槛的 `0/1` 以及 `uncertain` 不作为正负例计入主指标，但仍保留在候选排序中并占据名次。需报告不确定/低置信度配对数量及候选池覆盖率。
- **区间估计：** 建议按 `item_group_id` 进行配对 cluster bootstrap，报告方法间差值的 95% 区间；目前脚本默认 2,000 次抽样，随机种子为 42。独立物品组较少时区间仅作谨慎的不确定性描述，不等同因果证明。
- **候选池参考线：** 可附报均匀随机排序的解析期望值，说明候选池难度；不把它称为模型或第四种方法。

Hit Rate@5、配对差值与其区间，以及各指标的分析单位须在查看 test 结果前由导师确认。样本量计划依据独立物品组、获批试标数据及导师认可的精度/可行性标准制定；在此之前不填写统计功效或样本数结论。

## 3.7 运行成本和错误分析

分别记录每个方法的 API 调用耗时、成功/失败、错误类别、输入/输出 token 与实际费用，并记录日期、API 模型名、提示词/预处理版本及匿名记录编号。不得记录密钥、参与者姓名、联系方式或可反查身份的字段。离线评估脚本本身读取既有 `photo_scores.csv`，不会调用 DeepSeek；API 分数必须先按批准方案生成。

由排名详情生成逐查询人工复核表，列出漏掉的确认正例、前五名中的确认负例和未判定候选。研究者对错误原因作人工分类，例如图片质量、类别、可见特征、地点/时间、标签不确定或其他。不得让模型分数代替人工复核。
