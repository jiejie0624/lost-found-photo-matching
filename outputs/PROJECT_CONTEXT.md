# FYP 项目上下文：失物照片配对系统

> 这是本项目的长期上下文和当前事实来源。后续继续讨论或开发前先读本文件，并更新其中的状态、决定和待确认事项。

## 项目概念

为失主和拾获者提供失物记录发布与候选配对服务。用户上传物品照片，填写物品类别、地点和大概时间。系统用视觉模型提取可见特征，再结合类别、地点、时间检索并排序可能匹配的记录，最后由用户确认。

## 用户与约束

- 用户是计算机科学本科生。
- FYP 时间：约 12 个月。
- 用户说编程经验无需作为前置条件；规划时按可边学边做考虑。
- 用户表示预算不是当前限制，曾询问粗略费用；需持续留意 API、存储和托管成本。
- 用户不需要先了解学校要求；目前没有提供学校的额外硬性要求。
- 用户最初要求用简单中文讨论。
- 用户要求：先确认计划，再开始开发。用户随后明确说“start”，已授权开始实现当前建议的 MVP。
- 用户之前说“现在先不要写代码或创建文件”，后来明确要求“generate some files that you can refer everytime when you need”；因此本次创建的是规划和参考资料，不是产品代码。

## 当前建议研究方向（待用户确认）

将研究重点放在不同匹配方法的效果比较，而非仅实现上传网站。

### 候选研究问题

1. 加入照片分析后，真实匹配进入前几个候选的能力是否优于只用地点和时间？
2. 结合照片特征、地点和时间，能否将真实配对排在更前面？
3. 用户是否能轻松发布记录，并判断系统推荐是否有用？

以上仍是建议，需在用户确认计划后再固定。

## 建议最小可行版本（待确认）

- 用户发布“丢失”或“拾获”记录，上传照片并填写类别、地点和大概时间。
- 视觉模型从照片中提取类别、主颜色、品牌（看得清时）及明显特征。
- 先按类别、地点和时间过滤，再按属性相似度排序候选。
- 仅对少数靠前候选进行照片复核，减少费用并降低不相关比较。
- 用户查看候选、提出认领；双方确认前不公开完整联系方式或所有验证细节。
- 管理员可以处理重复、违规和明显错误的记录。
- 第一版暂不包含即时聊天、支付、原生手机 App、地图导航或人脸识别。

## 建议的匹配设计

采用“先筛选，再排序，再人工确认”：

1. 使用记录方向（丢失对拾获）、类别、地点距离和时间差筛选。
2. 对颜色、品牌、物品类型和显著特征计算初始相似度。
3. 可让视觉模型复核少量候选照片，并要求它给出可解释的相似点和不确定点。
4. 排名只用于提示，不作为所有权或物品身份的证明；由用户确认。

建议设置不调用视觉 API 的基线方法，供研究比较和 API 故障时使用。匹配权重和模型提示词后续应通过数据调整，不要把初始权重当作已验证结论。

## 当前实现技术栈

- Python + FastAPI：本地 MVP 后端。
- SQLite：本地记录数据库；云端配置 `DATABASE_URL` 后使用 PostgreSQL。
- 静态 HTML、CSS 和 JavaScript：简洁响应式中文网页。
- 本地运行时图片存储在本机；配置 Vercel Blob 后保存到 Blob。上传后用 Pillow 校正方向并重新编码，以移除 EXIF 元数据。
- 配置 `DEEPSEEK_API_KEY` 后，在发布记录时调用 DeepSeek 视觉 API 提取属性；未配置或调用失败时仍可按表单信息匹配。
- 当前匹配先按表单及 DeepSeek 提取属性排序，再让 DeepSeek 直接比较前 5 个候选照片并重排；API 不可用时退回属性排序。界面参考分不是配对概率。

此技术栈是为本地原型的低门槛和快速启动作出的实现选择。

## 评估建议

可执行的离线评估草案见 [`RESEARCH_AND_EVALUATION_PLAN.md`](RESEARCH_AND_EVALUATION_PLAN.md)。其中数据规模、伦理审批和参与者安排尚待导师确认。
数据字段及配对标注规则草案见 [`DATASET_AND_ANNOTATION_GUIDE.md`](DATASET_AND_ANNOTATION_GUIDE.md)，空白 CSV 模板也在 `outputs/`。
当前应用组件、接口、数据流和限制见 [`SYSTEM_ARCHITECTURE.md`](SYSTEM_ARCHITECTURE.md)。
当前启发式分数、文本相似度和排序规则见 [`MATCHING_ALGORITHM.md`](MATCHING_ALGORITHM.md)。

- 建立人工标注的失物与拾获配对数据集；尽量征得照片拍摄者同意，不使用未经授权的真实个人资料。
- 比较：用户填写信息的表单基线与再加入结构化视觉属性后的排序；候选照片复核可作为后续扩展。
- 报告 Hit Rate@5 / Recall@5、MRR@5、响应时间、失败率及实际 API 用量估算费用。
- 做小规模用户任务测试，观察发布和查找是否容易，并收集易用性反馈。
- 若涉及真实参与者或个人数据，先遵守学校研究伦理流程。
- 防止数据泄漏：同一件物品的照片或近重复记录不应同时出现在训练/调参数据和测试数据中。

## 主要风险与缓解方向

- 外观相似会造成误配：展示证据和不确定性，由用户确认。
- 数据少且配对难收集：先用经同意、人工标注的小型数据集做可复现实验。
- 照片隐私与 EXIF 定位：上传时移除 EXIF，限制照片访问，不公开联系方式。
- 假认领：可要求认领者提供未公开的物品细节，再让发布者判断。
- API 价格、能力或可用性变化：保留本地属性/元数据基线和可替换的 API 接口。
- 图片上传安全：限制文件类型、大小和访问权限，避免公开原始存储路径。

## API 能力和费用参考

截至 2026-10-09 查阅的 DeepSeek 官方文档：

- 用户指定使用 DeepSeek-V4.1-Flash。官方 API 调用名称是 `deepseek-flash`，而且支持图片输入；应用代码默认值已经是该 ID。只有启动后端时配置 `DEEPSEEK_API_KEY`，上传记录才会实际调用 API。详见 [官方更新日志](https://api-docs.deepseek.com/updates/) 和 [Vision 文档](https://api-docs.deepseek.com/guides/vision/)。
- 官方视觉文档列出 JPEG、PNG、GIF、WebP。图像以 token 计费，价格可能变化，调用前请查看 [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)。
- 官方价格表按模型、输入缓存命中/未命中、输出及高峰/非高峰列价；价格会变动，开发前应重新查阅 [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/)。
- 对“每个查询分析 1 张新照片，并比较最多 10 张候选照片”的假设，先前粗略估计 1,000 次查询约 US$2–5。此估算依赖图片 token、文字提示和输出长度，不能当成报价；照片存储、托管和数据库费用另计。

## 当前状态（2026-10-10）

**总体：应用演示原型已实现并部署；FYP 研究、实验和论文尚未完成。**

### 已实现/部署

- 手机与电脑浏览器网页；发布失物/拾获记录、公开浏览、显示前 5 个候选及匹配依据。
- DeepSeek 图像属性提取和候选照片直接比较代码；默认模型 ID 为 `deepseek-flash`。用户已在 Vercel 添加 `DEEPSEEK_API_KEY`，但最新一次真实线上图像分析尚未独立验收。
- Neon Auth 注册/登录，Neon PostgreSQL 保存记录，Vercel Blob 保存图片；登录用户可管理自己发布的记录。
- 记录 90 天期限和每日 Vercel Cron 清理。未带密钥访问清理端点得到 401，确认其密钥校验已开启。
- GitHub `main` 已与本地 `main` 同步。当前线上网站为 `https://lost-found-photo-matching-fyp.vercel.app/`。
- 2026-10-10 对线上首页、`/login`、`/my-records`、静态登录脚本、静态记录脚本、Auth 配置、健康接口和公开记录接口进行只读检查，均返回 HTTP 200；已登录的“我的记录”页正常显示，当前账号没有记录。该检查没有验证注册/登录提交、发布、AI 调用、匹配、关闭/删除或过期清理完整流程，也没有发送 DeepSeek 请求。

### 研究材料与工具

- 已有 Proposal、文献综述起步笔记、相关工作矩阵、数据/标注指南、算法和系统架构说明；这些是草案，不是导师批准的最终方案。2026-10-10 已根据 PLOS ONE 与 Springer 出版方全文/页面修正文献笔记：LostNet 同时有类别筛选和感知哈希候选排序；Springer 章节正式引用年份为 2026（2025 年首次在线）；当前研究空缺仍未通过系统检索证实。
- 新增空白 API 实验调用日志模板及导师讨论清单，列出研究范围、数据/伦理、第三方 API、样本设计、标注和评估的待确认事项。它们用于准备研究与沟通，不代表已有调用记录、导师答复或学校审批。
- 离线评估工具支持表单基线、视觉属性方法，以及导入 `photo_scores.csv` 的候选照片比较方法；会输出按物品组重抽样的配对 cluster bootstrap 置信区间。评估时，不确定和低置信度候选仍留在排名中，但只有达到阈值的 0/1 标签计入指标；每个查询必须标注同一 split 中的全部拾获候选。另有只读 CSV 数据预检脚本和双人标注一致性分析工具；前者检查字段、时间、授权标记、物品分组、配对标签结构和候选覆盖，后者报告原始一致率、混淆表与 Cohen's kappa。二者都不能替代人工核验或伦理审批。评估尚未用真实研究数据运行。
- 新增 `scripts/analyze_ranking_errors.py`，可将逐候选排名详情整理为逐查询人工复核表，列出漏掉的确认正例、前 K 名的确认负例和未判定候选；错配原因仍需研究者人工填写。尚未用真实数据生成或核对复核表。
- `outputs/records_template.csv`、`pair_labels_template.csv`、`photo_scores_template.csv`、`experiment_log_template.csv` 均为空白模板；**目前没有真实标注数据或实验结果**。
