## 项目概念

为失主和拾获者提供失物记录发布与候选配对服务。用户上传物品照片，填写物品类别、地点和大概时间。系统用视觉模型提取可见特征，再结合类别、地点、时间检索并排序可能匹配的记录，最后由用户确认。

## 用户与约束

- 用户是计算机科学本科生。
- FYP 时间：约 12 个月。

- 用户之前说“现在先不要写代码或创建文件”，后来明确要求“generate some files that you can refer everytime when you need”；因此本次创建的是规划和参考资料，不是产品代码。

## 当前建议研究方向（待用户确认）

将研究重点放在不同匹配方法的效果比较，而非仅实现上传网站。

### 候选研究问题

1. 加入照片分析后，真实匹配进入前几个候选的能力是否优于只用地点和时间？
2. 结合照片特征、地点和时间，能否将真实配对排在更前面？
3. 用户是否能轻松发布记录，并判断系统推荐是否有用？

以上仍是建议，需在用户确认计划后再固定。

## 建议最小可行版本（待确认）

- 用户发布“丢失”或“拾获”记录，上传照片并填写类别、地点和大概时间。
- 视觉模型从照片中提取类别、主颜色、品牌（看得清时）及明显特征。
- 先按类别、地点和时间过滤，再按属性相似度排序候选。
- 仅对少数靠前候选进行照片复核，减少费用并降低不相关比较。
- 用户查看候选、提出认领；双方确认前不公开完整联系方式或所有验证细节。
- 管理员可以处理重复、违规和明显错误的记录。
- 第一版暂不包含即时聊天、支付、原生手机 App、地图导航或人脸识别。

## 建议的匹配设计

采用“先筛选，再排序，再人工确认”：

1. 使用记录方向（丢失对拾获）、类别、地点距离和时间差筛选。
2. 对颜色、品牌、物品类型和显著特征计算初始相似度。
3. 可让视觉模型复核少量候选照片，并要求它给出可解释的相似点和不确定点。
4. 排名只用于提示，不作为所有权或物品身份的证明；由用户确认。

建议设置不调用视觉 API 的基线方法，供研究比较和 API 故障时使用。匹配权重和模型提示词后续应通过数据调整，不要把初始权重当作已验证结论。

## 当前实现技术栈

- Python + FastAPI：本地 MVP 后端。
- SQLite：本地记录数据库；云端配置 `DATABASE_URL` 后使用 PostgreSQL。
- 静态 HTML、CSS 和 JavaScript：简洁响应式中文网页。
- 本地运行时图片存储在本机；配置 Vercel Blob 后保存到 Blob。上传后用 Pillow 校正方向并重新编码，以移除 EXIF 元数据。
- 发布者逐条明确同意 AI 处理后，配置 `DEEPSEEK_API_KEY` 才会调用 DeepSeek 视觉 API 提取属性；未同意、未配置或调用失败时仍可按表单信息匹配。数据库新增 `ai_processing_allowed`，旧记录迁移后默认为未同意。
- 匹配先按表单及视觉属性排序；直接比较照片时要求查询记录和候选记录双方均同意 AI 处理，最多比较 5 个候选。应用授权不代表学校伦理审批或研究参与者同意；数据集指南另设 `external_ai_consent`，视觉属性未获第三方 AI 授权时预检会报错。界面参考分不是配对概率。

此技术栈是为本地原型的低门槛和快速启动作出的实现选择。

## 主要风险与缓解方向

- 外观相似会造成误配：展示证据和不确定性，由用户确认。
- 数据少且配对难收集：先用经同意、人工标注的小型数据集做可复现实验。
- 照片隐私与 EXIF 定位：上传时移除 EXIF，限制照片访问，不公开联系方式。
- 假认领：可要求认领者提供未公开的物品细节，再让发布者判断。
- API 价格、能力或可用性变化：保留本地属性/元数据基线和可替换的 API 接口。
- 图片上传安全：限制文件类型、大小和访问权限，避免公开原始存储路径。
